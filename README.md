на данном этапе мы создаём сам синтаксис компеляция в sql будет реализована позже.
основная идея это структура ориентированность тоесть библиотека сама знает какой параметр от какого зависит и между какими таблицами можно сделать join.
следующая идея представлять бд не как таблици а как вложенные классы примерно как в
graphQL или david spivak Categorical databases ближе даже ко второму тк идея что типы данных number str date можно тоже рассматривать как таблици просто бесконечные.
`core` библиотека где есть базовые классы и операции

- генерируемый по бд файл соструктурой бд `generated_bd_schema`

основные идеи синтаксиса
любая колонка это объект например `buyer: User[DealsSrs]`
тип User определяет какие есть зависимые значения тоесть те значения которые я могу однозначно определить для каждого юзера они доступны через .
например `buyer.email` или `buyer.regDate`
значение в скопках показывает откуда моя цепочка началась этот аргумент важен для арифметических операций я могу складывать умножать только метрики которые начинаются из одного `Source`.
теперь осталось определить агрегацию. чтобы посчитать сумму покупок юзера мне нужно определить

0. функцию `aggSum`
1. метрику `deals.amount_usd`
2. путь к значению по которому будет group by `deals.buyer`

`user_spend = aggSum(deals.amount_usd, deals.buyer)`
важное свойство аггрегационных функций они меняют `Source`. у user_spend `Source` не `DealsSrs` а `UserSrs`
тк `user_spend` однозначно определено для каждого юзера это и показывает `Source`
для того чтобы использовать вычисленный `user_spend` в дальнейших выражениях можно использовать оператор >> он аналогичен . по действию но позволяет соединять 2 независимых объекта

основная идея это автокомплит компилятр всегда знает какой тип а объекта и какие у него есть зависимые параметры + возможность использовать функции модули цыклы то что в обычном sql очень сложно и некрасиво + метрика ориентированость и структура данных позволяет указывать более сложные взаимосвязи чем в обычной бд
